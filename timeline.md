# Loop Lite — Timeline

Brief, dated log of what got implemented when. See [PROJECT.md](PROJECT.md) for the current working/missing snapshot.

## Session 1 — 2026-10-01

**Summary: core Loop Lite is functionally complete and confirmed working live.** Hold F24 (Caps Lock, remapped via keyd) → drag the mouse or press an arrow key to pick one of 8 directions, shown live via a transparent bordered outline at the target position plus a small center indicator (sticky — relaxing your hand doesn't cancel the pick) → release F24 and the active window snaps there on its own screen. Esc or releasing with no direction cancels cleanly. Hyperkey+Enter maximizes, Hyperkey+Backspace minimizes. Built as a compiled KWin C++ effect plugin (not a KWin script — scripts can't track continuous mouse movement while a key is held), verified against the real KWin 6.7.5 headers on this machine, not guessed APIs. Still open for a future session: a real radial-menu visual (currently a plain circle), a KCM settings page (padding, outline styling, configurable keybinds), and trimming the debug logging. Full detail below; see [PROJECT.md](PROJECT.md) for the live working/missing snapshot.

- Scaffolded the project as a compiled KWin C++ effect (`QuickSceneEffect` subclass), after confirming pure KWin *scripts* can't track continuous mouse movement while a key is held — verified against the actual installed KWin 6.7.5 headers rather than guessed APIs.
- Built CMake project; fixed two real build breaks found by actually compiling (missing `vulkan-headers`, a contradictory `<kcfgfile name=... arg="true">` in the kcfg, C++20 not being set). First clean build + link against KWin 6.7.5.
- Implemented direction detection (`snapcalculator.cpp`): 8-way direction from accumulated pointer delta past a deadzone, with configurable top/bottom-half mapping.
- Implemented the input/state machine in `loopliteeffect.cpp`: F24 global shortcut arms the effect, exclusive keyboard grab + mouse interception while held, snap applied via `Window::moveResize()` on F24 release, cancel via Esc or releasing with no direction chosen.
- Added Hyperkey+Enter (maximize) / Hyperkey+Backspace (minimize) via an extensible key-action table.
- Installed and configured `keyd` (Caps Lock → F24), confirmed active.
- Built, installed (`cmake --install`), enabled in kwinrc, and ran it for the first time. **First live result: mostly works, but the whole screen blanks to black during the hold, direction only seems to register while the mouse is actively moving, and arrow keys do nothing.**
- Diagnosed and fixed the black screen: the QQuickWindow backing the overlay scene defaults to an opaque clear color. Found the fix by reading KWin's own shipped Cube effect QML, which works around the exact same thing by binding the window's `color` to `"transparent"`. Applied the same binding in `Overlay.qml`.
- Diagnosed the "only triggers while actively moving" complaint: direction was being recomputed from scratch on every pointer event and reverting to `None` whenever the cumulative drag fell back inside the deadzone (e.g. hand relaxing before release). Made direction selection **sticky** — it only changes when the pointer clears the deadzone in a *new* direction, never reverts to `None` on its own.
- Added arrow-key support: while armed, Left/Right/Up/Down set the placement directly (cardinal only; diagonals still need the mouse), sharing the same `setDirection()` path as the pointer logic.
- Created this timeline and `PROJECT.md` for ongoing status tracking.
- Second live test (after discovering the toggle-based reload doesn't actually swap the loaded `.so` — fixed by restarting `plasma-kwin_wayland.service`, the supported Plasma 6 mechanism for this): black screen still present, direction still needed continuous movement, arrow keys appeared not to work.
- Tried switching the overlay to `KWin::Outline` + `KWin::OnScreenNotification` (the real mechanisms behind the native drag-to-edge tiling preview and the volume/brightness OSD) to sidestep the `QuickSceneEffect` rendering entirely. **Dead end**: confirmed via `nm -D` that neither class is actually exported from `libkwin.so` — their headers are installed but the symbols are compiled directly into the `kwin_wayland` executable, not available to out-of-tree plugins. Reverted to `QuickSceneEffect`.
- Added heavy debug logging (`qCWarning`) and had the user retest while being recorded. The journal gave a definitive answer: **arrow keys were already working correctly** (log shows Left/Up/Right/Down all setting the right direction) — the user's report was from a pre-rebuild test. The real, confirmed bug: a single F24 press produced 6–14 `arm()` calls at the same timestamp. Caps Lock/F24 **auto-repeats** at the OS level while held, re-firing the global shortcut every ~40ms, and each call reset `m_accumulatedDelta`/`m_direction` back to zero and tore down/recreated the overlay view. That's the entire "needs continuous movement" bug. Fixed with a re-entrancy guard in `arm()` (ignore the trigger if already armed).
- The log did not conclusively show `window->moveResize()` executing (that specific log line never appeared, likely lost to journald rate-limiting during the burst, not necessarily a real second bug) — added a clearer log line for both the success and failure paths of applying the snap, to confirm on the next test.
- Black screen cause still unconfirmed — may partly have been caused by the same repeated arm()/view-recreation churn; needs retesting now that arm() is idempotent.
- Verified the toggle-reload theory directly with a build-marker log line: installed a new marker, toggled the effect off/on + reconfigured, checked the log — **still the old marker**. Confirms toggle-reload genuinely never reloads compiled code (not a one-off fluke).
- Asked the user to try `systemctl --user restart plasma-kwin_wayland.service` again as the only other known way to force a reload. **This caused a hard lockup** — froze completely after the sudo password was submitted, requiring a hard power-cycle to recover. This command must never be suggested again on this machine.
- Established the only confirmed-safe reload path: a full, normal logout/login through Plasma's own menu. Each real live test now costs a full logout/login, so changes should be batched before asking for one.
- **Confirmed via a real logout/login test**: the arm() re-entrancy fix works — holding F24, dragging to a direction, relaxing the hand, and releasing now correctly snaps to the last-picked direction. The sticky-direction bug is resolved.
- User is tracking their own feature backlog in `Todo.md`. Cross-referenced it against project status; next up from that list: transparent background (still open — worth noting the *previous* "zero effect" test of the transparency binding happened while arm() was still thrashing the view 6-14x per hold, so that result may itself have been contaminated and isn't necessarily proof the binding approach is wrong) and an outline preview of the target geometry in the system accent color.
- Implemented the outline preview: `LoopLiteEffect::setDirection()` now computes the target rect, converts it to screen-local coordinates (`target.translated(-screen->geometryF().topLeft())`), and pushes it to the QML root item as `outlineX/Y/Width/Height` + `outlineVisible`. `Overlay.qml` draws it as a transparent-fill `Rectangle` with a `Kirigami.Theme.highlightColor` border, reusing the already-working `root->setProperty()` push mechanism from the direction indicator.
- Tested live (screenshot): outline preview renders correctly and in the right position/size — but background is still fully black, now on a confirmed-clean (non-thrashed) session. **This conclusively proves `QuickSceneEffect`'s backing surface is always opaque**, independent of the arm() thrashing bug — the `Window.color = "transparent"` binding genuinely has no effect. It appears to be a hard constraint of this class (built for full-screen takeover effects like Overview/Cube, not a see-through HUD).
- First pragmatic attempt: shrink the `QuickSceneView` itself to exactly the target rect via `setGeometry()`, merging the outline+indicator into one panel. Tested live (screenshot): the panel showed at the wrong position/size entirely ("not proportional"), and the separate center indicator was (expectedly, but unpopularly) gone. Root cause of the position bug: `view->setGeometry()` is scoped to that screen's own output, not the global virtual-desktop space `clientArea()` returns rects in — needed the same screen-local translation the QML coordinates already required. Fixed, but then asked the user whether they actually wanted the merged design at all, since it was a lossy compromise.
- User pushed back on "it can't be transparent" and asked for other options — right call. Re-examined the problem from scratch via `nm -D` on `libkwin.so` (not just headers) and found `QuickViewItem` (an internal friend class of `OffscreenQuickView` that would let its content be composited elsewhere) is not exported either — confirms `OffscreenQuickView`'s rendered texture genuinely cannot be hand-composited from outside KWin's own internals.
- **Real breakthrough**: realized `QuickSceneEffect` was the wrong mechanism entirely. KWin is a Qt application that creates its own chrome (decorations, tooltips, the task switcher, `Outline`, `OnScreenNotification`) as ordinary internal `QQuickWindow`s via a custom QPA platform plugin — these go through the *normal* per-window compositing path (real alpha blending) rather than the Effect-paintScreen override path that's hard-coded opaque for scene effects. Since our plugin runs in the same process, it should be able to create plain `QQuickWindow`s (via the public, fully standard `QQuickView` class) and get the same treatment — no KWin-specific linking/ABI risk at all, since this is 100% standard Qt API.
- Rewrote the effect back to a plain `KWin::Effect` (not `QuickSceneEffect`) with two independent `QQuickView` overlays: `Outline.qml` (transparent-fill bordered rect at the target geometry, true global coordinates this time — no more screen-local translation needed since these are genuine top-level windows) and `Indicator.qml` (the small circle, back at screen-center, in its own small transparent window so the rounded shape doesn't show a black square). Both windows use `Qt::FramelessWindowHint | Qt::WindowStaysOnTopHint | Qt::Tool | Qt::WindowDoesNotAcceptFocus | Qt::WindowTransparentForInput` and `setColor(Qt::transparent)`.
- Built successfully. **Confirmed working live**: real transparency achieved, both overlays (outline + center indicator) position correctly, window snaps correctly on release. Core Loop Lite interaction is functionally complete end-to-end: hold F24, drag or arrow-key to a sticky direction, see the live preview, release to snap.

**End of Session 1.**
